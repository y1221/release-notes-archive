# Visual Studio 2026 バージョン 18.12.0 リリースノート

**2026 年 11 月 10 日**リリース。

### IDE

**ソリューション エクスプローラーのファイル システム ビューで作業する**

> _リポジトリの物理レイアウトを参照し、ソリューションを切り替え、ソリューション エクスプローラーのファイル システム ビューからプロジェクト コマンドを実行します。_
> 
> ソリューション エクスプローラーの **\[ファイル システム\]** ビューでは、ソリューションやプロジェクトの操作にすぐアクセスできる状態を保ちながら、リポジトリの物理的なレイアウトを確認できます。
> 
> ##### リポジトリの物理的なレイアウトを確認する
> 
> **\[ファイル システム\]** ビューに切り替えると、プロジェクト外のドキュメント、ビルド用アセット、構成ファイルなど、ディスク上の実際のファイル構成を確認できます。 リポジトリ内ではリポジトリのルートが、それ以外ではソリューション フォルダーがビューの起点になります。 プロジェクトの構造や依存関係、読み込まれているプロジェクトを確認するには、**\[ソリューション\]** ビューに戻ります。
> 
> ![リポジトリのファイル システム ビューを示すソリューション エクスプローラー](media/18.12/se-filesystem-animation.gif)
> 
> 両方のレイアウトを同時に表示するには、コンテキスト メニューから **\[新しいソリューション エクスプローラー ビュー\]** を選択し、**\[ソリューション\]** ビューと **\[ファイル システム\]** ビューを並べて表示します。 ビューを切り替えるだけなら、別のウィンドウを開く必要はありません。
> 
> ##### \[ファイル システム\] ビューからソリューションを切り替える
> 
> リポジトリに複数のソリューションが含まれている場合、物理的なフォルダー レイアウトから移動することなく、別のソリューションを開くことができます。 **\[ファイル システム\]** ビューでソリューション ファイルをダブルクリックし、現在の Visual Studio インスタンスで開くか、新しいインスタンスで開くかを選択します。
> 
> ![[新しいインスタンスで開く] ボタンと [開く] ボタンが表示された [ソリューションの切り替え] ダイアログ](media/18.12/file-system-switch-solution.png)
> 
> ##### ビューを切り替えずにプロジェクト コマンドを実行する
> 
> **\[ファイル システム\]** ビューでプロジェクトを右クリックして、**\[ビルド\]**、**\[リビルド\]**、**\[クリーン\]**、または**\[スタートアップ プロジェクトに設定\]** を使用します。 ソリューション外のファイルを探索したり、同じビューから一般的なプロジェクト コマンドを使用したりできます。
> 
> これらのアクションは、アクティブなソリューション内のプロジェクトに適用されます。 そのソリューション外のプロジェクトでは、ビルド アクションは有効になりません。
> 
> ![ビルド コマンドとスタートアップ コマンドを含むファイル システム ビュー プロジェクト メニュー](media/18.12/solution-file-system-actions-2.png)  

**フォルダーを開くで MSBuild の依存関係を復元する**

> _最初にソリューションを開かずに、\[フォルダーを開く\] から MSBuild の復元を実行します。_
> 
> **\[フォルダーを開く\]** で作業する場合、最初にソリューションを開くことなく MSBuild 依存関係を準備できます。 サポートされているソリューションまたはプロジェクト ファイルを右クリックし、**\[復元\]** を選択すると、フォルダーの既存のビルド アクション ワークフローを通じて MSBuild 復元ターゲットが実行されます。
> 
> 検出されたソリューションに属するプロジェクトの場合、このアクションによってそのソリューション固有のターゲット設定が維持されます。 これにより、フォルダー ビューから作業している場合でも、プロジェクトのソリューション コンテキスト内で復元を維持できます。
> 
> このアクションは CMake やその他のビルド プロバイダーには適用されず、C++ の `.vcxproj` ファイルも除外されます。
> 
> ![フォルダーを開くで MSBuild プロジェクトコンテキスト メニューから復元を実行する](media/18.12/open-folder-msbuild-restore-1.gif)  

**更新されたオプションのその他の設定**

> _更新されたオプション エクスペリエンスには、ユーザー設定をリセットせずに、製品の更新、開発コンテナー、グラフィックス キャプチャの設定が含まれます。_
> 
> 更新された \[オプション\] では、保存済みの設定をリセットすることなく、より多くの既存の設定項目を同じ画面で管理できるようになりました。
> 
> ##### 製品の更新を管理する
> 
> 更新された \[オプション\] では、**\[バックグラウンド ダウンロード\]**、**\[操作モード\]**、およびサポートされている **\[終了時に更新\]** の動作を管理できます。 既存の既定値や保存済みの設定は維持され、インストーラーを使った操作も引き続き利用できます。
> 
> 表示される設定項目は、製品で利用できる機能と組織のポリシーに応じて変わります。 ポリシーによって **\[終了時に更新\]** が無効になっている場合は、変更可能な設定項目の代わりに、その説明が表示されます。
> 
> ##### Dev Containers の設定を確認する
> 
> \[更新されたオプション\] で **クロス プラットフォーム →開発コンテナー** を開き、既存のコンテナーの基本設定を管理します。 保存済みの設定やホストの選択内容は、既存の設定ストアと引き続き同期されるため、コンテナー環境を設定し直す必要はありません。 この統合機能は、CMake Linux 拡張機能に含まれています。
> 
> ##### グラフィックス キャプチャを設定する
> 
> 既存のグラフィックス **\[キャプチャ\]** 設定 7 項目が、更新された \[オプション\] に表示されるようになりました。 互換モードと HUD のオプションには肯定形のラベルが使用されます。また、別のプロセスが共有キャプチャ設定の値を変更すると、その変更が設定ページにも反映されます。 移行後の設定ページが従来のプレースホルダーに置き換わるため、同じ設定を扱うページが重複して表示されることはありません。  

**\[出力\] ウィンドウの ANSI 色 📣**

> _未加工のエスケープ シーケンスでメッセージを隠すことなく、ANSI 色のツール出力をレンダリングします。_
> 
> ツールが ANSI カラーで色付けされたメッセージを出力する場合、テキストに生のエスケープ シーケンスが混ざった状態で表示される代わりに、**\[出力\]** ウィンドウでそれらの色を直接確認できるようになりました。
> 
> Visual Studio のビジュアル エクスペリエンス設定で色付けされた出力を有効にして試してみてください。 このオプションは初期状態では無効になっているため、カラー レンダリングを選択するまでは、そのままの生の出力が維持されます。
> 
> ![ANSI 色のツール メッセージを表示する出力ウィンドウ](media/18.12/output-window-ansi-colors-1.png)
> 
> このオプションを有効にすると、Visual Studio は表示テキストからエスケープ シーケンスを削除し、それらの色の切り替えを維持します。 選択、コピー、および検索では、非表示のシーケンスではなく、表示されているテキストが使用されます。
> 
> エスケープ シーケンスを含め、ツールが出力した元の出力がそのまま必要な場合は、このオプションをオフのままにします。
> 
> 📣 _フィードバックを共有し、会話を続けるには [、機能チケット](https://developercommunity.visualstudio.com/idea/777436/colorized-output-window.html) を参照してください。_  

**コンパクトな言語サーバーホバーヒントを読む 📣**

> _言語サーバーのホバー ヒントでは、構文に色付きのシグネチャと例がコンパクト ビューに表示され、コードの内容が少なくなります。_
> 
> 言語サーバーのホバー ヒントでは、コード フェンスで囲まれたコードが、従来の大きな汎用パネルではなく、構文に応じて色分けされたコンパクトな形式で表示されるようになりました。 シグネチャや使用例がエディター上で占める領域が小さくなり、目立つ位置にあった **\[コードのコピー\]** コントロールは削除されました。
> 
> ![構文に色付きの署名と例を含むコンパクトな Rust ホバー ヒント](media/18.12/compact-language-server-hover-after.png)
> 
> Markdown のリンクとキーボードによる操作は、引き続き利用できます。 埋め込まれたコードは表示専用であり、フォーカスを取得したりテキストを選択したりできる別のエディターではありません。 この変更は言語サーバーのホバー コンテンツが対象であり、すべてのクイック ヒント プロバイダーに適用されるわけではありません。
> 
> 📣 _フィードバックを共有し、会話を続けるには [、機能チケット](https://developercommunity.visualstudio.com/t/The-JavaScriptTypeScript-Native-Languag/11150826) を参照してください。_  

**その他の画像形式をプレビューする 📣**

> _ソリューション エクスプローラーエディターを開かずに、TIFF、DDS、WebP など、より多くの画像形式をプレビューします。_
> 
> ソリューション エクスプローラーで画像にマウス ポインターを合わせると、従来対応していた PNG、JPEG、GIF、BMP、ICO に加え、TIFF、DDS、JPEG XR、HD Photo、Windows Media Photo、WebP もプレビューできます。 **\[フォルダーを開く\]** でもプレビューを利用でき、エディターで扱える画像形式に対応しています。
> 
> WebP など一部の形式では、対応する Windows の画像コーデックが必要になる場合があります。
> 
> ![ホバー時に画像のプレビューを表示するソリューション エクスプローラー](media/18.12/image-formats-thumbnail.png)
> 
> 📣 _フィードバックを共有し、会話を続けるには [、機能チケット](https://developercommunity.visualstudio.com/t/Solution-Explorer-image-hover-preview-la/11144795) を参照してください。_

>

>

**構文の強調表示と TextMate の更新**

> _構文の強調表示が改善された他のファイルの種類を読み、より高速なプレビュー TextMate マッチャーをお試しください。_
> 
> Visual Studio のエディターでは、より多くのファイル形式で構文に応じた色分けが改善されました。 TextMate のマッチング機能にも、専用のプレビュー オプションが追加されました。
> 
> ##### 更新された文法による TOML および Rust の編集
> 
> TOML ファイルは、新しい TextMate 文法によって、構文の強調表示、コードの折りたたみ、中括弧の自動補完、およびコメントの作成/解除コマンドをサポートするようになりました。
> 
> ![Visual Studio エディターで構文が強調表示されている TOML ファイル](media/18.12/textmate-updates.png)
> 
> 更新された Rust の TextMate 文法により、構文の強調表示が向上し、より新しい Rust 言語の機能が認識されるようになります。
> 
> ##### レジストリ ファイルとソリューション ファイルをより簡単に閲覧する
> 
> レジストリ(`.reg`) およびパッケージ定義 (`.pkgdef`) ファイルで、コメント、セクション、割り当て、文字列、削除構文、型指定された値が強調表示されるようになりました。 パッケージ定義の強調表示で、`qword:` 値と `#include` ディレクティブも認識されます。 ソリューション ファイルは構造も強調表示されます。
> 
> ![構文に色付きのセクション、文字列、および数値を含むレジストリ ファイル](media/18.12/registry-solution-syntax-highlighting-2.png)
> 
> ![構文に色付きのプロジェクトと構成セクションを含むソリューション ファイル](media/18.12/solution-file-syntax-coloring.png)
> 
> ##### より高速になった TextMate マッチングを試す
> 
> 新しいマッチャーを試すには、**プレビュー機能** の **\[高速な TextMate 構文マッピングを使用する\]** を有効にします。 対象となる構文規則をまとめて検索し、サポートされていないケースについては既存のマッチャーを維持します。
> 
> 1.09 MB の TypeScript フィクスチャを 1 つ使用したローカル ベンチマークでは、解析時間が 8.989 秒から 1.882 秒に短縮されました。 この結果はそのフィクスチャにおけるものであり、すべてのファイルで改善が保証されるわけではありません。 このマッチャーは、JavaScript または TypeScript の言語サービスに置き換わるものではありません。  

### 生産性

**コメント内のインライン候補を制御する 📣**

> _コードで無効にせずに、コメント内の自動インライン候補をオフにします。_
> 
> コード内のインライン候補は有効にしたまま、コメント内での自動表示だけを無効にできます。 \[ **ツール\]→\[オプション\]→\[テキスト エディタ\]→環境設定** を開き、\[ **コメントに候補を表示**\]をオフにします。
> 
> 従来の動作を維持するため、この設定は既定で有効になっています。C# の XML ドキュメント コメントと C++ のコメントも対象です。 必要に応じて、コメント内でも手動で入力補完を呼び出せます。
> 
> ![コメントの書き込み中にインライン候補が無効になりました](media/18.12/autocomplete-in-comments-thumbnail.png)
> 
> 📣 _フィードバックを共有し、会話を続けるには [、機能チケット](https://developercommunity.visualstudio.com/t/Turn-off-autocomplete-in-comments/10983048) を参照してください。_  

**エディター ルーラーを使用して行の長さを追跡する 📣**

> _リポジトリの行長規則に従うように、構成済みの列にエディター ガイドを表示します。_
> 
> エディターにガイド線が追加され、コードを書きながらリポジトリで指定された行の長さを確認できるようになりました。
> 
> ![エディターで構成された列幅に表示される垂直ルーラー ガイド](media/18.12/max-length-ruler.gif)
> 
> `rulers`を使用して、1 つ以上のガイドを表示します。
> 
> ```
> rulers = 80, 120
> ```
> 
> `rulers`が指定されていない場合、Visual Studioは`max_line_length`にフォールバックします。
> 
> ```
> max_line_length = 120
> ```
> 
> 両方のプロパティが存在する場合は、 `rulers` が優先されます。 継承された値を抑制するには、いずれかのプロパティを `unset` に設定します。 ガイドの色はVisual Studioテーマに従い、\[**ツール\] → \[オプション\] → \[環境\] →フォントと色**でカスタマイズできます。
> 
> 📣 _フィードバックを共有し、会話を続けるには [、機能チケット](https://developercommunity.visualstudio.com/t/support-max-line-length-in-editorconfig-for-visual/567214) を参照してください。_  

**マークダウン リンクと見出しナビゲーション 📣**

> _ファイルをドラッグして Markdown リンクを作成し、リンクを直接クリックして他のドキュメントの見出しに移動します。_
> 
> Markdown へのリンクと画像の追加が、ドラッグ アンド ドロップするのと同じくらい簡単になりました。 ファイルを ソリューション エクスプローラー または Windows エクスプローラーから Markdown エディターにドラッグすると、Visual Studio は適切な Markdown 構文をドロップ位置に挿入します。 通常ファイルはリンクになり、サポートされているイメージ ファイルはイメージ参照になります。
> 
> ![マークダウン ドキュメントにファイルをドラッグ アンド ドロップする](media/18.12/markdown-drop-file-and-preview.gif)
> 
> Visual Studioはパスの詳細を処理します。 リンクは、正規化された区切り記号とエンコードされたスペースを含む、現在の Markdown ドキュメントに対する相対パスを使用するため、複数のコンピューター間で移植可能で、すぐに使用できます。 元のファイルはそのままであるため、ワークフローを中断することなくドキュメントを作成できます。
> 
> ##### 見出しへのリンクをたどる
> 
> Markdown プレビューで、`[Installation](setup.md#installation)` などのリンクをたどると、ターゲット ファイルが開き、そのエディターとプレビューの両方が一致する見出しまでスクロールされます。
> 
> これはスタンドアロン プレビューでも機能します。 Visual Studio は、見出しまでスクロールする前に、Mermaid ダイアグラムなどの非同期コンテンツを含め、移動先のプレビューのレンダリングが完了するまで待機します。
> 
> 📣 _フィードバックを共有し、会話を続けるには、 [機能チケット 1](https://developercommunity.visualstudio.com/t/Markdown-editor-fails-to-insert-referenc/11147171)、 [機能チケット 2](https://developercommunity.visualstudio.com/t/Support-for-Cross-Document-Anchor-Links/10993308) をご覧ください。_

### Performance

**応答性の高いVisual Studio**

> _大規模なソリューションの読み込みと終了、デザイナーとダイアログの開き方、状態と診断の更新に費やす時間を短縮できます。_
> 
> Visual Studio では、大規模なソリューションの読み込みや終了、デザイナーやダイアログの起動、UI の更新時に発生する重複処理が削減されました。 メリットを享受するために新しい設定を有効にする必要はありません。
> 
> ##### 大規模な C++ ソリューションをすばやく開く
> 
> Visual Studio では、C++ のコメント タスクの更新時にプロジェクト ディレクトリの情報を再利用するようになりました。また、ソリューションを開く際に実行されていた、負荷が高く不要なテレメトリ クエリを削除しました。 PR のテスト シナリオでは、**Parse Solution** フェーズの所要時間が Chromium で約 20%、Unreal Engine で 9% 短縮されました。 これらは該当フェーズの測定結果であり、ソリューション全体の読み込み時間が同じ割合で短縮されることを保証するものではありません。
> 
> ##### 大規模なソリューションをより短い待ち時間で閉じる
> 
> ソリューションを閉じる際、削除されるプロジェクトごとに、開いているすべてのドキュメントを再スキャンしなくなりました。 また、Visual Studio は、終了処理中の繰り返しのファイル監視クリーンアップや、キャッシュされた C++ プロジェクトの不要なアクティブ化を回避します。 これらの変更により、多くのプロジェクトや追跡対象ファイルを持つソリューションを閉じるために必要な処理が削減されます。
> 
> ##### ソース管理の更新時の応答性を維持する
> 
> ソース管理のステータスに大規模な変更があると、ソリューション エクスプローラーの多数のアイコンが一度に更新されることがあります。 Visual Studio は、その処理を制限されたバッチ単位で実行するようになったため、すべての保留中のアイコン更新を待つのではなく、バッチ処理の合間に UI を描画できるようになりました。 ステータス インジケーターと Git ワークフローは、これまでと変わりません。
> 
> ![ソース管理の状態アイコンの更新をソリューション エクスプローラーする](media/18.12/solution-source-control-icon-performance-1.gif)
> 
> ##### 大規模なエラー一覧の結果セットの更新を高速化
> 
> レガシー診断プロバイダーは、エラー一覧の更新時に、並べ替えられたコレクションに対して各結果を繰り返し挿入することを回避するようになりました。 これにより、プロバイダーが多数の項目を一度に報告する際の UI 処理が削減されます。 この変更は診断結果を維持し、すべての診断ソースではなく、このレガシー プロバイダーのパスを対象としています。
> 
> ##### 待ち時間が短縮された \[新しい項目の追加\]
> 
> **\[新しい項目の追加\]** を開くと、Visual Studio は、まず現在のプロジェクト ファミリのテンプレート登録とキャッシュを読み込みます。 ダイアログを表示する前に登録済みのすべてのプロジェクト タイプの初期化をしなくなりました。
> 
> テンプレートの選択肢、プロジェクト切り替え時の動作、およびユーザー テンプレートの更新機能は、これまでと変わりません。 これは、Visual Studio が処理を実行するタイミングを変更するものであり、プロジェクトで使用できるテンプレートを変更するものではありません。
> 
> ![.NET コンソール プロジェクトのテンプレートを表示する新しい項目を追加する](media/18.12/add-new-item-dialog-performance-1.png)
> 
> ##### デザイナーの起動時の処理を削減する
> 
> -   **Windows フォーム:** 複雑なデザイナーが、すべてのネイティブ ラッパー オブジェクトに対して同じレジストリとローダーの検出を繰り返さなくなりました。 Visual Studio では、オブジェクトごとに新しいラッパーを作成しながら、該当するスレッドでアクティブ化の準備処理を再利用します。 この改善は準備処理の負荷を削減するものであり、フォームの初期化コードを最適化するものではありません。
> -   **UWP XAML:** デザイナーは、同じ情報に対して完全なアプリ パッケージを再び開いて解析する代わりに、SDK マニフェストから既に解決されているフレームワーク依存関係 ID を再利用します。 識別情報が不完全な場合は、従来のパスに基づく確認処理も引き続き利用できます。 この改善の対象は UWP デザイナーの起動処理であり、すべての種類の XAML プロジェクトに適用されるわけではありません。  
>

**MCP を使用してデバッガーの状態を検査する**

> _Visual Studio Debugger MCP では、条件付きブレークポイントと、フレームのローカルと引数の構造化された検査が追加されます。_
> 
> Visual Studio Debugger MCP を使用すると、エージェントは実行を停止し、デバッグ フレームで使用可能な値を検査するより正確な方法が提供されます。
> 
> ##### 条件付きブレークポイントを設定する
> 
> ログポイントとの組み合わせを含め、ソースブレークポイントと関数ブレークポイントで式とヒットカウント条件を構成します。 エージェントは、すべてのヒットを中断するのではなく、条件が満たされた場合にのみ停止したり、対象の情報を収集したりできます。

> ##### ローカルと引数を検査する
> 
> `debugger_get_locals` ツールは、選択した停止スタック フレームの引数とローカル変数を返します。 結果には、名前、型、値、または評価診断、および各値を展開できるかどうかが含まれます。
> 
> エージェントは、式名を推測するのではなく、次に検査する対象を選択する前に、フレームの使用可能な値を検出できます。 このツールは、使用できない、または失敗した評価を報告します。これは、すべての値をすべてのデバッグ状態で評価できることを意味するわけではありません。

**NuGet パッケージ管理の機能強化**

> _パッケージの更新の最小有効期間を設定し、パッケージ ソースに対するより明確な認証プロンプトを表示します。_
> 
> NuGet にパッケージの有効期間を制御する機能が追加され、認証が必要なパッケージ ソースを特定しやすくなりました。
> 
> ##### パッケージ更新のクールダウンを設定する
> 
> 新しく公開されたパッケージ バージョンに、アシスト機能による更新の対象として選択されるまでの時間を設けることができます。 **\[パッケージ ソース\]** でフィードの **\[最小公開期間 (時間)\]** を設定します。 たとえば、72 という値を設定すると、公開されてから 3 日未満のバージョンが、アシスト機能による更新によって自動的に選択されるのを防ぐことができます。 既定値は 0 時間であるため、クールダウンを設定するまでは、既存の動作がそのまま維持されます。
> 
> ![発行期間が 72 時間以上のパッケージ ソース設定](media/18.12/nuget-package-source-cooldown.png)
> 
> **\[最小公開期間の例外\]** を使用すると、`System.*` などのパッケージ ID またはプレフィックス パターンを期間チェックの対象から除外できます。 これにより、すべてのパッケージに一律で同じポリシーを適用するのではなく、遅延を適用する場所を個別に選択できます。
> 
> ![パッケージ プレフィックスとパッケージ ID を一覧表示する発行期間の最小例外](media/18.12/nuget-cooldown-exceptions.png)
> 
> また、`--min-publish-age-hours` または `dotnet nuget add source` の `dotnet nuget update source` でポリシーを設定することもできます。 パッケージの追加および更新コマンドでも、バージョンを選択する際にこのポリシーが適用されます。 クールダウンの計算が必要なフローティング バージョンは `NU1020` で失敗します。
> 
> クールダウンはバージョン選択の目安となるものであり、復元全体を一律で制限するものではありません。 明示的なバージョンであれば、クールダウン中であっても引き続き復元することができます。 クールダウンによってセキュリティ修正プログラムやその他の更新プログラムの適用が遅れる可能性があるため、例外の選択は慎重に行ってください。
> 
> ##### パッケージ ソースのサインイン プロンプトを識別する
> 
> 認証が必要なフィードからサインインを求められた際、Windows の資格情報ダイアログが、プロキシ認証という不正確な説明ではなく、パッケージ ソースの認証として正しく識別して表示するようになりました。 特にネットワーク プロキシと併せて認証が必要なフィードを使用している場合に、どのサービスで資格情報が必要とされているのかを識別できるようになります。
> 
> 以前と同様に、パッケージ ソースで要求される資格情報を入力します。 これはプロンプトの説明を修正するものであり、フィードが受け入れる資格情報を変更したり、独立したプロキシ認証のワークフローを置き換えたりするものではありません。  

### C++

**C++ のインデックス作成とインクルード スキャンの機能強化**

> _インデックス作成が既定で有効になっており、インクルード スキャン中の作業の繰り返しが少ない C++ コードベース間を移動します。_
> 
> Visual Studio、C++ プロジェクトに対してコードベース全体のインデックス作成が既定で有効になりました。 インデックスを使用すると、コードのナビゲーションと色分けがより速くなり、Copilotでの C++ の質問のリポジトリ コンテキストが提供されます。
> 
> インデックス作成がバックグラウンドで進行すると、結果が使用可能になります。 リソースの使用状況と完全性のインデックス作成は、コードベースのサイズと構成によって異なります。
> 
> ##### 繰り返しのインクルード スキャン作業を減らす
> 
> Visual Studioでは、インクルード スキャン中に正規化された検索パスと解決されたディレクトリ ノードが再利用されるようになりました。 同じファイルへの繰り返しの参照でも、現在のパス内でそのファイルの種類の分類が再利用されます。
> 
> これにより、インクルード パスやプロジェクト設定の変更を必要とせずに、共有ヘッダーを持つ大規模なコードベースが役立ちます。 状況依存検索、カスタム ファイル名マッピング、およびオープン ファイル言語のオーバーライドは、既存の動作を保持します。  

**C++ プロジェクト構成の更新**

> _新しい CMake 構成は既定でプリセットに設定され、C++23 プロジェクト設定では安定したコンパイラ スイッチが選択されます。_
> 
> C++ プロジェクト構成では、新しい CMake 構成の移植可能な既定値と、C++23 を対象とするプロジェクトの安定したコンパイラ スイッチが得られます。
> 
> ##### 新しい構成に CMake プリセットを使用する
> 
> Visual Studio新しい CMake 構成を追加するときに、既定で `CMakePresets.json` を作成して使用するようになりました。 これにより、新しいプロジェクトは、Visual Studio、CMake コマンド ライン ツール、およびその他のエディターで動作する移植可能な構成形式が提供されます。
> 
> `CMakeSettings.json`を使用する既存のリポジトリは引き続きそのファイルを使用し、自動的には移行されません。 Teams では、CMake プリセットをコミットして、Visual Studioとコマンド ラインオートメーションの間で一貫したビルド設定を共有できます。
> 
> ![Visual Studio新しい構成に既定で CMake プリセットを使用するように構成されている](media/18.12/cpp-cmake-presets-by-default.png)
> 
> ##### 安定した C++23 スイッチを選択する
> 
> `LanguageStandard`の`stdcpp23`値が、非推奨の`/std:c++23preview`スペルではなく、安定した MSVC `/std:c++23` スイッチにマップされるようになりました。 `stdcpp23`を使用する既存のプロジェクトは、プロジェクト ファイルを変更せずにマッピングを取得します。
> 
> 安定したスイッチをサポートするツールセットを使用します。 プレビュースペルが必要な古いツールセットまたはコンパイラを意図的に使用する場合は、アップグレードするか、この言語標準の選択を削除し**、追加オプション**を使用して`/std:c++23preview`を指定します。

> 皆様からのフィードバックをお待ちしております。 問題が発生した場合は、[Visual Studio Developer Community](https://developercommunity.visualstudio.com/cpp) までご報告ください。
> 
> このリリースには、MSVC 14.51 以降のコンパイラ フロントエンド、バックエンド、リンカー、標準ライブラリ、および関連ツールにおける変更が含まれています。
> 
> ##### C++ 標準規格への準拠
> 
> -   **C++23 言語モード:**`/std:c++23`を使用して C++23 言語規則を選択します。 既存の `/std:c++23preview` という表記も引き続き機能し、`/std:c++23` のエイリアスとなります。 プレビュー版の形式は現在非推奨となっており、将来のアップデートで削除される予定です。
> -   **即時エスカレーション:** C++23 即時エスカレーション (P2564R3) を使用すると、対象となる `constexpr` 関数とラムダは、使用が必要になったときに即時になります。 この機能は C++23 以降のモードで有効になります。C++20 ビルドでは、`/Zc:immediateEscalation` を指定することでオプトインできます。
> -   **Unicode 識別子:** C++23 モードと C23 モードでは、P3658R1からの数学的互換性識別子の範囲が認識されます。
> -   **モジュールでの Constexpr の割り当て:**モジュール インターフェイスは、`new T[n]`式を含む`constexpr`関数を表すことができます。
> -   **プリプロセッサの動作:**`_Pragma` は、より多くのマクロ拡張ケースで機能し、 `/E`でサポートされています。
> -   **Constexpr cmath:** C++ コンパイル時 cmath 関数のサポートは、/std:c++23 では既定ではオフのままであり、/Zc:cmath スイッチを使用して有効にすることができます。 詳細については、[https://devblogs.microsoft.com/cppblog/msvc-c23-constexpr-cmath-with-llvm-libc/](https://devblogs.microsoft.com/cppblog/msvc-c23-constexpr-cmath-with-llvm-libc/) を参照してください。
> 
> ##### C++/CLI、C、および言語ツール
> 
> -   `/clr` は、C++23 以降のモードで使用できるようになりました。
> -   オプトインの `/Zc:functionToObjectPtr` スイッチは、関数ポインターから`void*` への暗黙的な変換を拒否します。
> -   コンパイラは、仮想基底クラスを含む一部の `constexpr` コンストラクター テンプレートのインスタンス化を受け付けるようになりました。 定数評価中にこれらの仮想基底クラスを構築することは引き続きサポートされていないため、これは `constexpr` 関数の宣言チェックに限定されます。
> -   C コードでは、構造体がそのフレキシブル配列メンバー用のストレージなしで割り当てられた場合、またはフレキシブル配列メンバーを持つ構造体が値渡しされた場合に、C4815 および C4816 が警告するようになりました。
> -   Linux C++ の IntelliSense パーサーは、C++20 および C++23 の標準オプションを対応する言語モードにマッピングします。
> -   実引数依存の名前探索において、モジュールからエクスポートされていないより多くの名前を処理できるようになり、ネストされたテンプレートやモジュールのインスタンス化が失敗しにくくなりました。
> -   モジュールのシリアル化において、クラスのデータ メンバーやテンプレート情報がより一貫して保持されます。。 複数のモジュールがヘッダー ユニットを共有している場合も、型のマージがより適切に機能します。
> -   ヘッダー ユニットでマクロの空白が保持されるため、文字列化されたマクロが往復処理後も維持されます。 モジュール処理で、グローバル モジュール フラグメントで最初に定義された型も、より確実に処理されます。
> -   数学組み込み関数および数学ヘッダーが、モジュールや定数評価においてより一貫して機能します。
> -   キャレット診断のメモリ使用量が削減され、いくつかの診断メッセージにおいて、元のソースコードの式がより正確に再現されます。
> -   プリプロセッサ診断で、形式に誤りがある定数式や入れ子になった定数式がより正確に特定されます。
> -   コンパイラが、無効な型トレイトの入力や、形式に誤りがある関数パラメータのスコープをより一貫して処理します。
> -   コンパイラは、非推奨の非純粋仮想関数をオーバーライドしたときに警告します。
> 
> ##### コード生成と最適化
> 
> **インライン展開:**
> 
> -   LTCG において、呼び出し側が小さな戻り値オブジェクトのどのフィールドを読み取っているかが考慮されるようになり、インライン化の際、使用されないフィールドを計算する処理を破棄できるようになりました。
> -   プログラム全体の最適化において、インライン化を行うことでローカル オブジェクトの一部が露出し、使用されていないストアを削除できるようになる場合、そのインライン化が優先されます。
> -   ループ内から呼び出される小さなラッパーを介して、アウトライン化された大きなループ ボディをインライン化できるようになりました。
> -   PGO を使用する場合、プロファイル、サイズ、および増加の制限が許す限り、サイズが最適化された小さな仮想関数のターゲットを投機的にインライン化できます。
> -   インライナーがアグリゲートの割り当てを介して関数ポインターの値を追跡できるようになり、テンプレート アダプターにおける間接呼び出しの機会がさらに保持されます。
> -   型ベースの脱仮想化が、プロファイルガイド付きインライン化と連携して機能します。 ホット/コールド情報により、コールド コードがホットな呼び出し元に元へ引き込まれるのをより効果的に防げるようになりました。
> 
> **ループとスカラーの最適化:**
> 
> -   各ロードがすべての反復で実行され、かつエイリアス関係にあるポインタ間でも安全であることが証明された後、コンパイラはより多くのループ不変なロードをループ外に移動できます。
> -   等価比較ループにおいて、ループ間依存のある処理をより多く削減できるようになり、また強度削減がラップアラウンドする整数誘導変数の式をより多く処理できます。
> -   3 つ以上の乗算で共通の除数がある場合、オプティマイザーが 1 つの逆数を計算してそれを再利用できるようになり、繰り返しの除算を復元せずにすむようになりました。
> -   エイリアス関係にあるフィールドを介したコピー伝播が既定で有効になり、サイズが既知の `memcpy` および `memset` 操作を認識します。
> -   x64 の条件付き選択において、より多くの非ゼロ定数および安全なエイリアス関係にあるオペランドを処理できます。
> -   符号なし比較および誘導変数の範囲から、以降の最適化に向けて、より多くの非ゼロ、順序、および非オーバーフローに関する事実が確立されます。
> -   スカラー条件式において、より多くの値の等価性、入力値、乗算、およびシフトに関する単純化が行われるようになりました。
> -   メモリ干渉を判定する際、呼び出しにおいて `restrict` 引数がより正確に使用されるようになり、それらの呼び出し周辺でより多くの最適化が行われるようになりました。
> -   x86 オプティマイザーが、より多くのローカルおよびブロック間のコピー伝播を実行します。
> -   コンパイラが、より多くの回転イディオムや動的なビットフィールド抽出コントロールを認識するようになり、また、冗長な POPCNT ゼロ拡張を削除します。
> -   小さいアグリゲートの最適化において、パディングのみの割り当てを削除し、条件を満たす構造体全体のロードを分解し、また、該当するロードをローカルな `memcpy` 操作を通じて転送します。
> -   定数変換は、変換がそれ以外に有効である場合、`/fp:fast` なしでフォールドできます。
> -   より早い段階でのループ不変式移動や、より広範な式の再結合により、以降の最適化に向けて、より多くの処理を引き出せるようになりました。
> -   大きな関数ほど、繰り返される式がより多く再利用されます。 最小/最大式、混合符号比較のひし形、繰り返しベクトル要素抽出も、より多くのケースで単純化が行われるようになりました。
> -   `noexcept` 関数へのより多くの間接呼び出しが、末尾呼び出しに変換されます。 静的定数配列も、ストレージが不要になると消えるようになりました。
> -   ループ アンスイッチングがベクトル化の前に、より多くの入れ子になったループのケースを処理するようになり、一方で直線型ベクトル化が、より多くのマージされた値を処理します。
> -   ジャンプ チェーンや誘導変数が、有用な述語や符号情報を失うことなく、より多くのケースで単純化されます。
> -   コンパイラが、出力する属性データを削減し、例外リージョンのスキャン回数を減らし、極端なデッドユース探索を制限するとともに、大規模な連鎖関数式を、2 乗時間ではなく線形時間で処理します。
> 
> **ベクター化:**
> 
> -   x64 および ARM64 で、コンパイラが、分岐を通じて値を選択するより多くのコードをベクトル化します。
> -   `sum += a[i] - b[i]` のような整数リダクションを、ループ ベクタライザーが認識できる形式に再結合できます。
> -   x64 および ARM64 で、ベクトル ロードおよびベクトル ストアが、より早い段階でコピー伝播やスカラー置き換の対象になるようになりました。 フル幅ベクトルを分割することで有用なベクトル操作が破棄されてしまう場合に、分割せずにそのまま維持されます。
> -   ベクタライザーが、より多くの隣接アドレス パターンを認識するようになり、また、結果がベクトル レジスタに維持できる場合は、ユーザーが記述した SIMD 値のパックがより多く行われるようになりました。
> -   ループによって進められるパラメータ由来のポインターが、ローカル配列とエイリアス関係にないと認識されるケースが増え、不要なランタイム重複チェックを回避できます。
> -   ループ ベクタライザーが、条件を満たすメモリ間のみのスワップやマルチストリーム コピーを処理できるようになり、これには単純型の配列に対する `std::swap` も含まれます。
> -   その後の条件式で共有されるより多くのループ制御式が、ループの後に単純化されます。
> 
> ##### ARM64
> 
> -   ARM64 で、関数パラメーターに基づく構造体配列のループを含め、関連するロードおよびストア間のアドレス計算が共有されるようになりました。 これにより、繰り返される算術演算が削除され、ペアのロードおよびストアを行うためのより多くの機会が生まれるようになりました。
> -   既知の NEON 定数を、不要なデータ ロードを行うことなく構築できます。 スカラー ロード、ブロードキャスト、レーン挿入も、より多くのケースで NEON ロード命令にフォールドされます。
> -   コンパイラが、より多くの NEON 構築およびレーン操作を組み合わせるようになり、未使用のレーン挿入を削除し、冗長なマスク比較を排除します。
> -   ループ ベクトライザーが、追加の `floor`、`ceil`、`trunc`、`round` 操作を処理するようになりました。。
> -   末尾呼び出しの判定が呼び出しごとに行われるようになり、同じ関数内にある 1 つの不適格な呼び出しが、別の適格な呼び出しの妨げになることがなくなりました。
> -   ARM64 および ARM64EC のインライン化で、浮動小数点レジスタやベクトル レジスタのプレッシャーが考慮されます。 これにより、利益をもたらすネイティブ ARM64 インラインを維持しつつ、制限のある ARM64EC ターゲットでの過度なスピルを回避できます。
> -   ネイティブ ARM64 SVE2 で、レーン指定された`svmullb` および `svmullt` 組み込み関数のコード生成と逆アセンブルがサポートされます。 実行には SVE2 対応ハードウェアが必要です。
> -   LUTI2 および LUTI4 ルックアップ テーブルのサポートに、BF16 形式が含まれるようになりました。 浮動小数点絶対値最小/最大命令や Common Short Sequence Compression の操作もサポートされます。 各ファミリは、対応するプロセッサ機能を必要とします。
> -   `ARM64_FPMR` `_ReadStatusReg`と`_WriteStatusReg`の FPMR レジスタに名前を付けます。armasm64 と逆アセンブラーは同じ名前を認識します。 実行には FEAT\_FPMR ハードウェアおよび OS のアクセス許可が必要です。
> -   ネイティブ ARM64 で `__preserve_none` および `[[msvc::musttail]]` がサポートされるようになり、これには特化したインタプリター ディスパッチも含まれます。 `__preserve_none` 呼び出し規約は C 言語専用であり、ARM64EC ではサポートされていません。
> -   `/feature:sme` を指定すると、コンパイラが、サポートされている外部宣言で SME 属性や ZA 状態の型を受け付けるようになりました。 条件を満たすスカラー `noexcept` 呼び出しが、必要なストリーミングモード遷移を実行できるようになり、これには選択された関数ポインタ、参照、プログラム全体、および制御フロー ガードのケースが含まれます。 ストリーミング関数定義、ZA 保持呼び出し、サポートされていないポインター形式、およびベクトルまたはアグリゲートの引数は、引き続きサポートされていません。 ARM64EC は除外されています。
> -   ネイティブ ARM64 CRT が、TPIDR2、ZA、および ZT0 用の AAPCS64 SME 状態管理ルーチンを提供します。 可用性はプロセッサおよびオペレーティング システムの状態サポートに依存し、ARM64EC は除外されます。
> -   ARM64 で、`/Zc:cmath` 数学ランタイムが浮動小数点環境をサポートします。 この初期実装では、数学エラーが `errno` ではなく浮動小数点例外を通じて報告されるようになっています。
> -   ARM64 スタック レイアウトで、互いに排他的な switch case 間でローカル変数用のスロットを再利用できるようになり、大規模な switch 文のフレーム サイズを大幅に削減できます。
> -   ステートレスな全要素が真である SVE 述語は、通常の安全性および収益性のチェックで許可される場合に、ループ外に移動できます。
> -   デッドコードであることが証明されたスイッチ エッジがスイッチ展開の前に削除されるようになり、より多くの制御フローおよび値の最適化が引き出せるようになりました。
> -   ビットフィールド操作で、可能な限りより狭い即値形式が使用されます。
> -   レジスタ割り当てで、より多くの隣接するロード ペアが維持されるようになり、頻繁に使用される値に対して、より適切なスピルや再マテリアル化の選択肢が選ばれるようになりました。
> -   使用レーン追跡が、より多くのスカラー浮動小数点演算にまたがって機能するようになり、不要なベクトル処理を引き出せるようになりました。
> -   コンパイラが、より多くのベクトル置換、レーンごとの回転、およびベクトル ビットクリア即値形式を認識します。
> -   SVE 比較や、MATCH、NMATCH、WHILE ファミリで、条件フラグがより効果的に再利用されます。 NEON から SVE へのブリッジ移動、上位レーンの浮動小数点抽出、および要素ごとの乗算アドレス指定でも、より短い命令シーケンスが生成されます。
> 
> ##### x64 および x86
> 
> -   速度最適化された x64 ビルドで、固定長の `memcmp` に対するより多くの戦略が用意されます。 256 バイトを超える条件を満たすコピーでは、大規模なインライン シーケンスの代わりにランタイム コピー パスが使用されます。
> -   x64 で、ジャンプ テーブルのアドレス計算の前にあるより多くの冗長なゼロ拡張が削除されるようになり、また、定数である 2 のべき乗による符号なし除算がシフト演算に低減されます。
> -   定数 `f64x2` の割り当てを組み合わせられるようになり、以降のベクトル操作が 1 つの 128 ビット定数ムーブにフォールドされるようになりました。
> -   32 ビット x86 ビルドで `fmin`、`fmax`、`copysign` を、ARM64 で `copysign` をインライン化できます。
> -   AVX2 および AVX-512 ターゲットで、メモリとの往復をすることなく、より小さなレジスタ値からより幅の広いベクトルを構築できます。
> -   AVX-512 コード生成は、組み込み関数オペランドに適切な VEX ムーブを使用し、ブレンドが続く対象の単一使用マスク付き算術演算を 1 つのマージ マスク演算にフォールドします。
> -   `/feature:APX` を使用するビルドは、より多くの算術および条件選択形式、より少ない冗長なムーブおよび比較、そしてスカラー整数ループのための APX を認識したアンローリングおよび強度削減の決定を獲得します。
> -   APX サポートは、現在 ABI、アセンブラ、逆アセンブラ、およびデバッグツールに及びます。 R30 と R31 は不揮発性で、レジスタ割り当てはそれらを `setjmp` 間でキル済みとして扱い、MASM および逆アセンブラは対象となる拡張レジスタ エンコーディングを処理し、DIA は APX レジスタ コンテキストを読み取ります。
> -   APX 有効の x64 コード生成は、対象となるオペランドをフォールドでき、より優れたスピル、再計算、およびフォールドの選択を行います。
> -   Unwind V3 のサポートは、現在、コード生成、リンク、ML64、DIA、およびバイナリ インストルメンテーションに及びます。 これは、チェーンされたランタイム関数レコード、大規模なプロローグおよびエピローグ、`.PUSHFRAME`/`.POPFRAME`、およびスタックウォーキングをカバーします。 ML64は `/unwindv3` を必要とします。コンパイラのエミッションは APX 関数に対してのみデフォルトで有効であり、スタック ウォーキングは V3 を認識するオペレーティング システムとデバッガーを必要とします。
> -   x64 は、対象となるアトミックな fetch-add シーケンスを含む、より多くの条件コードに安全な `INC`/`DEC` 形式を認識します。
> -   AVX2 の組み込み関数低レベル化は、条件を満たす `_mm_set_sd` および `_mm256_set1_pd` パスでの不要なスカラーからベクトルへのムーブを削除します。
> -   APX コード生成には、より多くの新しい宛先およびメモリ オペランド形式、対象となる INC/DEC および SUB シーケンスの短い LEA 置換、そしてより広範なシフト、比較、条件付き比較、条件付きムーブ、定数伝播のサポートが含まれます。
> -   すべてのビットが設定されたベクトル定数およびペアにされたレジスタ演算を含む関数は、より優れたコード生成を受け取ります。
> -   シフト範囲分析はハードウェアのシフト カウント マスクをモデル化し、隣接する 2 要素のダブル ストアはより効果的に結合します。
> -   `/O1` および `/Os` では、追加の事前割り当て最適化やサイズ認識命令コストによりコード サイズが削減されます。
> -   RDPRU はその必要な固定レジスタ制約を使用します。

> ##### 標準ライブラリ
> 
> 機能、LWG 懸案事項の解決、バグ修正、パフォーマンスの向上などごとにグループ化された、このリリースのすべての変更の完全なリストについては、「[STL チェンジログ - MSVC ビルド ツール 14.52](https://github.com/microsoft/STL/wiki/Changelog#msvc-build-tools-1452)」を参照してください。主なポイントは以下の通りです。
> 
> -   **P0533R9** "[](https://wg21.link/P0533R9) For `constexpr` And `<cmath>`" が実装されたため、STL は `<cstdlib>`です。
>     -   これは、最初は `/std:c++23 /Zc:cmath` でのみサポートされています。 今後のリリースで `/std:c++23` が `/Zc:cmath` を意味するようにすることを予定していますが、現在はオプトインです。 必要なコンパイラ機構が利用可能になると、Clang および EDG のサポートが有効になります。
>     -   詳細については、Cody Miller (MSVC コンパイラ フロントエンド 開発者) による「[MSVC C++23: constexpr cmath with LLVM Libc](https://devblogs.microsoft.com/cppblog/msvc-c23-constexpr-cmath-with-llvm-libc/)」および Michael Jones と Tue Ly (Google の LLVM-libc メンテナー) による「[Bringing Correctly Rounded Math to Production with LLVM-libc](https://devblogs.microsoft.com/cppblog/bringing-correctly-rounded-math-to-production-with-llvm-libc/)」をお読みください。
>     -   `/std:c++latest /Zc:cmath` では、主に C++26[P1383R2](https://wg21.link/P1383R2) の `constexpr` による `<cmath>` への追加機能を実装しています。 (まだ `<complex>` の変更はありません。) いくつかの関数は LLVM-libc によってまだ実装されておらず ([LLVM libc math status](https://libc.llvm.org/headers/math/index.html) を参照)、したがって、まだ `constexpr` ではありません。 `double` の場合、関数 `acosh`、`asinh`、`atanh`、`cosh`、`sinh`、`tanh`、`erf` がありません。 `float` および `double` の場合、関数 `erfc`、`lgamma`、`tgamma` がありません。 (MSVC は 64 ビットの `long double` を使用するため、各関数の 3 つ目の実装は必要ありません。) それらが利用可能になり次第、将来のリリースでそれらを `constexpr` として有効にします。
> -   標準のバグ修正である 19 件の LWG 問題解決。
>     -   標準で解決されたすべての LWG 問題は、マイクロソフトの [STL LWG 問題プロジェクト](https://github.com/orgs/microsoft/projects/1152/views/2)で追跡されます。
> -   いくつかのシナリオで `<regex>` 性能が向上しました。
>     -   この`<regex>`の継続的な正確性とパフォーマンスの見直し[について、ジュリア](https://github.com/muellerj2)ン・ミュラー(GitHubの@muellerj2)に感謝します。
> -   いくつかの STL アルゴリズムの ARM64 SVE ベクトル化された実装を追加しました。
>     -   また、以前に追加された ARM64/ARM64EC Neon ベクトル化された実装の一部におけるデグレードを修正し、パフォーマンスを向上させました。
>     -   この継続的なベクター化作業のために、アーム([GitHubの@hazzlim](https://github.com/hazzlim))でハリ・リマエに特別な感謝。
> 
> ##### AddressSanitizer
> 
> -   重複した隔離作業を削除することにより、ランタイム パフォーマンスを向上させました
> -   インターセプションのためのフォールバック命令長デコーダーとして MSDIS (MSVC 逆アセンブラ) を使用し、「認識されない命令」による失敗を削減します。 これは既定でオンで、ASAN\_OPTIONS=windows\_use\_msdis\_decoder=false で無効化できます。 手動命令デコーダーの代わりに MSDIS によってどの命令がインターセプトされたかを追跡するには、verbosity=3 を設定し、「MSDIS instruction decoder:」というプレフィックスが付いたログを検索します。
> -   ヒープ アドレス キャッシング、より効率的なメモリマップド ヒープ チェック、およびより高速なアロケータ フラグ割り当てを含むランタイム パフォーマンスの向上により、複数のランタイム シナリオにわたって大幅なパフォーマンス向上が得られます。

> ##### ビルド ツールと診断
> 
> -   C++ フロントエンドは、より多くの有効な指示初期化形式を受け入れます。
> -   C++ フロントエンドは、より深く入れ子にされた初期化子を受け入れ、レガシ プリプロセッサは、より大きなマクロ バッファーを許可します。
> -   Code Analysis SARIF の出力には、既定でルール名、説明、ヘルプ リンクが含まれ、利用可能な場合はタグも含まれています。
> -   LNK2022 および LNK4227 は、関連するメタデータ項目に名前を付けます。 LNK4323 は、欠落している ARM64EC/ ネイティブ オブジェクト ペアについて説明します。
> -   インクリメンタル リンクは、プログラム データベース ファイルから過剰な増加スペースをトリミングします。
> -   逆アセンブリ ライブラリは、MIPS32 および MIPS64 リリース 6 命令と ARM64 マトリックス状態開始/停止命令を認識します。
> -   `/analyze:log:format:sarifandxml`は、両方のCode Analysisログ形式を書き込みます。
> -   LNK4321 は、インポート ライブラリの生成中に重複した C++ モジュール エクスポートを特定します。
> -   C5089 は、`/fsanitize=address` を含む `/clr` と `/clr:netcore` の実験的な組み合わせを特定します。
> -   C++ では、2 つの新しいレベル 4 警告は、`HRESULT`/`SCODE` と `bool` のような型との間の暗黙的および明示的な変換を特定します。 それらは既定でオフであり、C には適用されません。
> -   オプトインの `/PDB4GBSTREAMS` オプションは、PDB グローバル/パブリック シンボル レコード ストリームのサイズ制限を約 4 GiB に引き上げます。 他の PDB ストリームは既存の制限を維持します。
> -   MASM および 逆アセンブリ ライブラリは、x86 `int1`/ICEBP 命令 (`0xF1`) を認識します。
> -   LTCG は、`extern` 宣言が型について一致しない場合に C4744 を出力します。
> -   イメージ ハッシュに PDB エイジが含まれなくなったため、 PE 再現性が向上します。
> -   タグベースの Code Analysis 警告グループは、ルールセット オーサリングを簡素化します。
> -   デバッガー クライアントは、ロードされたデータを破棄せずにプログラム データベース ファイル ハンドルを解放できるため、ファイルの再構築を早めることができます。 デバッグ情報はモジュール型とヘッダー ユニット型の統合の信頼性も高めます。
> -   デバッグ レコードは代替オブジェクト名を識別でき、型レコード処理は割り当てを少なくし、大規模なプログラムでのスループットを向上させます。
> -   リンカーやアセンブラの診断はより明確になり、形式に誤りがあるオブジェクト ファイル、ライブラリ、モジュール メタデータはより防御的に処理されます。

> _CMake プロジェクトのスキャンを繰り返しても、重複するプロジェクト検出通知がトリガーされなくなりました。_
> 
> CMake ワークスペースの繰り返しスキャンから重複するプロジェクト検出通知を削除し、プロジェクト検出中の不要な UI スレッドの作業を減らしました。
> 
> CMake プロジェクトを通常どおり開くか更新します。 Visual Studioは、新しく検出されたプロジェクト プロバイダーを報告しますが、そのワークスペース内で同じプロバイダーを繰り返し報告する必要はありません。  

**C++ 動的デバッグがプレビューから離れる**

> _プレビューとしてマークされなくなった機能を使用して、オンデマンド関数の最適化を使用して最適化された C++ コードをデバッグします。_
> 
> C++ 動的デバッグのプレビュー ラベルが削除されました。 プロジェクト のプロパティ ページとコンパイラ、リンカー、およびライブラリのオプションの説明で、更新されたラベルを使用して、オンデマンド関数の最適化を使用して、最適化されたコードを引き続きデバッグできます。
> 
> x64 C++ プロジェクトで使用するには、プロジェクトのプロパティを開き、\[ **構成プロパティ\] → \[詳細設定\] → \[C++ 動的デバッグを使用** する\] を **\[はい**\] に設定し、リビルドします。 このモードでは、プログラム全体の最適化がオフになります。
> 
> セットアップ手順と制限事項については、「 [C++ 動的デバッグ](/ja-jp/visualstudio/debugger/cpp-dynamic-debugging) 」を参照してください。  

**C++ のインクルードを解決するときの CPU 作業を削減する**

> _Visual Studioでは、大規模な C++ ソリューションでインクルード ファイルを解決するときにパス処理が繰り返されないようにします。_
> 
> 大規模な C++ ソリューションの解析中にインクルード ファイルを解決するときの CPU 作業が削減されました。 インクルード リゾルバーは、各検索で同じ動作を繰り返すのではなく、正規化されたインクルード パスとキャッシュされたディレクトリ参照を再利用します。
> 
> C++ コードを解析Visual Studio、この機能強化は自動的に適用されます。 プロジェクトのインクルード ディレクトリを変更したり、新しいオプションを有効にする必要はありません。  

**C++ プロジェクトの同時更新中にハングを回避する**

> _C++ プロジェクトの更新とバックグラウンド ディレクトリのインポートの間のデッドロックが解決されました。_
> 
> C++ プロジェクトの更新がバックグラウンド ディレクトリのインポートと重複したときに IDE がフリーズする可能性があるデッドロックが解決されました。 プロジェクト システムが、プロジェクト データベースへのアクセス中に共有キャッシュ ロックを保持しないようにしました。
> 
> この修正プログラムは、プロジェクト設定を変更することなく、既存の C++ プロジェクトに自動的に適用されます。  

**リモート CMake テストをより確実に実行する**

> _テスト エクスプローラーは、CMake テストを起動する前にリモート接続を確立し、一時的な接続エラーを再試行します。_
> 
> **テスト エクスプローラー**がリモート CMake プロジェクトでテストを検出したが、実行またはデバッグを試みたときにテストを **"実行しない**" のままにした場合を修正しました。 テストを開始する前に、 **テスト エクスプローラー** でリモート接続が確立され、一時的な接続エラーが再試行されるようになりました。
> 
> リモート Linux ターゲット用に構成された既存の CMake プロジェクトの場合は、 **テスト エクスプローラー** で検出されたテストを選択し、通常どおりに実行またはデバッグします。 接続のセットアップでは、取り消しも考慮されます。認証エラーと拒否されたホスト キーでは、基になる接続の問題を解決する必要があります。  

**Unreal プロジェクトで誤った再構築プロンプトを回避する 📣**

> _誤った古いプロンプトを表示せずに、既にビルドされている Unreal Engine プロジェクトのデバッグを開始します。_
> 
> 既にビルドされている Unreal Engine プロジェクトのデバッグを開始したときに表示される誤った古いプロンプトを修正しました。 以前は、プロジェクトを変更せずに **F5** キーを押しても、リビルドを求められる場合があります。
> 
> この修正プログラムは、影響を受ける Unreal Engine プロジェクトを含め、Visual Studioの組み込みの up-to-date チェックで必要なビルド状態情報を提供しない NMake 構成に適用されます。 プロジェクトをビルドし、通常どおり **F5** キーを押します。up-to-date チェックをグローバルに無効にする必要はありません。
> 
> 📣 _フィードバックを共有し、会話を続けるには [、機能チケット](https://developercommunity.visualstudio.com/t/Regression:-VS-2026-Fast-Up-to-Date-Chec/11031914) を参照してください。_  

### Extensibility

**複数の SDK ターゲットの拡張機能をビルドする 📣**

> _更新された拡張機能互換性モデルでは、Visual Studio 2026 SDK、SDK スタイルのプロジェクトの選択肢、および複数ターゲットの拡張機能ペイロードが追加されます。_
> 
> 更新された拡張機能の互換性モデルの一部として、Visual Studio 2026 バージョン 18.12 以降を特に対象とする初の Visual Studio SDK (VSSDK) を使用して、拡張機能を構築できるようになりました。
> 
> 拡張機能でこのターゲットで利用可能な API が必要な場合は、新しい SDK を使用します。 新しい SDK に向けて構築された拡張機能を Visual Studio Marketplace に公開することもできます。
> 
> 以前の Visual Studio バージョンもサポートしている場合、マルチターゲット ビルドを使用して、SDK ターゲットごとに個別のペイロードを生成し、1 つの Marketplace エントリの下でそれらを公開できます。 これにより、既存のユーザーが利用できる互換性のあるペイロードを維持しながら、より新しい API を導入することができます。
> 
> ##### プロジェクトのビルド スタイルを選択する
> 
> **\[モダン VSIX プロジェクト\]** テンプレートで、**\[トップレベルの Visual Studio SDK を使用する\]** をクリアして、明示的なパッケージ参照を持つ通常の `Microsoft.NET.Sdk` プロジェクトを作成します。 このオプションは、VSSDK、VisualStudio.Extensibility、およびハイブリッド拡張機能をサポートします。
> 
> トップレベルの SDK は、デフォルトで選択されたままになります。 既存の C# VSIX プロジェクトおよび空の VSIX プロジェクト テンプレートは引き続き利用できます。
> 
> ##### SDK ターゲットごとにペイロードをビルドする
> 
> 1 つの VSIX プロジェクトで複数のバージョンの Visual Studio SDK をターゲットにできます。 ビルド ツールはトップレベルの SDK とターゲット フレームワーク モニカーに対応しており、`TargetFrameworks` で宣言された SDK ターゲットごとに個別のペイロードを生成します。
> 
> ```
> <Project Sdk="Microsoft.VisualStudio.Sdk.Build">
>   <PropertyGroup>
>   <TargetFrameworks>vs17_14;vs18_12</TargetFrameworks>
>   <ExtensionType>VisualStudio.Extensibility</ExtensionType>
>   <LangVersion>latest</LangVersion>
>   </PropertyGroup>
> </Project>
> ```
> 
> 18.12 向けのペイロードでは、そのターゲットで導入された API を使用できます。一方、17.14 向けのペイロードは、互換性のある旧バージョンのインストール環境でも引き続き利用できます。 これらのペイロードは、Marketplace の 1 つの掲載ページでまとめてアップロードし、管理できます。 Visual Studio 2022 以降に対応する拡張機能の掲載ページでは、複数のペイロードを登録できます。
> 
> ![2026 年と 2022 年Visual StudioダウンロードVisual Studioマーケットプレース拡張機能の一覧](media/18.12/extension-marketplace-payloads.png)
> 
> ##### 一致するペイロードを自動的にインストールする
> 
> 複数のターゲットに対応する Marketplace の拡張機能をインストールまたは更新すると、Visual Studio が互換性のある最適なペイロードを選択します。 表示される拡張機能のエントリは 1 つだけであり、自分で SDK ターゲットを選択する必要はありません。
> 
> たとえば、17.14 向けと 18.12 向けのペイロードが用意されている場合、Visual Studio 17.14 には 17.14 向け、Visual Studio 18.12 には 18.12 向けのペイロードが適用されます。 更新時も、同じ選択ロジックが使用されます。
> 
> 📣 _フィードバックを共有し、会話を続けるには [、機能チケット](https://developercommunity.visualstudio.com/t/When-will-MicrosoftVisualStudioInterop/10997805) を参照してください。_
